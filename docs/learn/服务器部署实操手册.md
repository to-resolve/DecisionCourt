# 服务器部署实操手册（手动版）

> 记录 2026-09-20 把 DecisionCourt 部署到腾讯云 CVM 的完整过程。
> 每条命令都给「**原始写法 + 为什么**」，可以照着从头做一遍。
>
> 本文是**学习材料**（放在 `docs/learn/`），不是项目主文档。主文档见 `docs/` 下其他文件。

---

## 0. 先搞清楚：谁做了什么

上一轮部署里，绝大部分命令是我通过一个 Python SSH 脚本远程执行的，你只在控制台点了几个按钮。对照表：

| 环节 | 我实际用的方式 | 你手动练习时的等价操作 |
|---|---|---|
| 本机 SSH 连接 | `paramiko`（Python 库）读写密码 | Windows 自带 `ssh` 命令，交互输密码 |
| 服务器初始化 | 上传 `bootstrap-server.sh` 远程执行 | 手动 `ssh` 进去，逐条敲（见 §5） |
| 传代码 | SFTP 上传 tar.gz | `git clone` 或 `scp`（见 §6） |
| 改 .env | `step3-env.sh` 用 sed 批量改 | `nano .env` 手动改（见 §7） |
| 构建启动 | `nohup docker compose up -d --build &` | 同一条命令，直接前台跑 |
| 验证 | 远程 `curl` | 本地浏览器 + `curl.exe` |

**为什么我要用 paramiko？** Windows 没有 `sshpass`，没法在非交互的脚本里输密码；而且我要连续执行几十条命令、看长日志、传文件。**你自己练习时完全不需要它**——Windows 自带的 `ssh` 是交互式的，输密码、敲命令都很直观，反而更适合学习。

## 2. 第一步：连上服务器

### 2.1 用 Windows 自带的 ssh（推荐入门）

打开 **PowerShell** 或 **Windows Terminal**，敲：

```powershell
ssh ubuntu@49.235.176.27
```

第一次连接会看到：

```
The authenticity of host '49.235.176.27' can't be established.
ED25519 key fingerprint is SHA256:xxxxx...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

输入 `yes` 回车。这是一次性的主机指纹确认——SSH 靠它防止有人中间冒充你的服务器。确认过之后指纹存进 `~/.ssh/known_hosts`，以后不再问。

然后提示 `ubuntu@49.235.176.27's password:`，**粘贴密码时屏幕上不会有任何显示**（不是卡住了，这是正常的安全设计），直接回车。

看到提示符变成 `ubuntu@VM-xx-xx-ubuntu:~$` 就成功了。先跑三条命令熟悉环境：

```bash
whoami              # 我是谁 → ubuntu
hostname            # 主机名
cat /etc/os-release | head -3   # 系统版本
nproc               # CPU 核数 → 2
free -m             # 内存 → 约 1967MB，swap 行初始是 0
df -h /             # 磁盘 → 50G
```

**退出连接**：敲 `exit`，或按 `Ctrl+D`。

### 2.2 密码登录失败怎么排查（我踩过的坑）

如果你遇到 `Permission denied (publickey,password)`，按顺序检查：

**① 用户名对不对**（90% 的原因）

```powershell
ssh ubuntu@49.235.176.27    # 腾讯云 Ubuntu 镜像用这个
```

不要用 `root`（密码登录被禁）、不要用 `lighthouse`（那是轻量服务器的用户）。

**② 密码有没有串字符**

复制密码时注意：控制台里显示的密码如果有前导短横线，那可能**不是密码的一部分**（是列表的符号）。密码里的 `!` `@` `#` 在某些终端有特殊含义——用**双引号包起来**最保险：

```powershell
ssh ubuntu@49.235.176.27 "-NrfppjgGY_C8FD"
```

（这只是举例，实际这样传密码并不规范，只是说明引号的作用。）

**③ 连续失败会被临时限流**

腾讯云 CVM 的 sshd 有防爆破机制，同一 IP 连续失败几次后会**临时拒绝所有认证请求**（即使密码是对的）。我中间就被锁了两次，等 3-5 分钟自动恢复。

所以：**不要反复重试**，确认用户名和密码后一次性登录。

**④ 换密码后必须重启实例**

在控制台「重置密码」后，新密码**关机重启才生效**：

```text
控制台 → 实例 → 更多 → 实例状态 → 关机
       → 更多 → 密码/密钥 → 重置密码 → 填新密码
       → 开机（约 2 分钟）
```

**⑤ 终极手段：重置密码 + 换成密钥登录**

如果密码怎么都不行，直接跳到 §3 用密钥（更可靠，也是生产标准）。

### 2.3 进阶：VS Code Remote-SSH（强烈推荐）

装了密钥之后，用 VS Code 连服务器写代码/改配置，比在终端里敲 `nano` 舒服得多：

1. VS Code 装扩展 **Remote - SSH**（微软官方）
2. `Ctrl+Shift+P` → `Remote-SSH: Connect to Host` → `ubuntu@49.235.176.27`
3. 连上后 `文件 → 打开文件夹` → `/opt/DecisionCourt`

现在你的 VS Code 里能直接看到服务器文件、内置终端，改 `.env` 和改本地文件一样。**日常运维 80% 的时间可以用这个搞定。**

## 3. 第二步：免密登录（SSH 密钥）

### 3.1 为什么要做这一步

| 维度 | 密码登录 | 密钥登录 |
|---|---|---|
| 安全性 | 可被暴力破解（你的服务器 22 端口每分钟都在被人扫） | 数学上不可暴力破解 |
| 体验 | 每次输密码 | 直接进 |
| 自动化 | **无法用于 CI/CD** | 是 GitHub Actions 部署的唯一方式 |
| 失败限流 | 有（见 §2.2③） | 几乎不会触发 |

第 4 阶段的 CI/CD 强制要求密钥，所以这一步不是可选优化，是必经之路。

### 3.2 本机生成密钥（如果还没有）

先检查：

```powershell
ls ~/.ssh
```

有 `id_ed25519` 和 `id_ed25519.pub` 就跳过。没有的话生成：

```powershell
ssh-keygen -t ed25519 -C "你的邮箱@example.com"
```

一路回车（密码短语留空 = 免密使用，练习场景够用）。

生成的是**一对**：
- `id_ed25519` —— **私钥**，绝对不外泄，留在你电脑里
- `id_ed25519.pub` —— **公钥**，要装到服务器上

### 3.3 把公钥装到服务器

`ssh-copy-id` 在 Windows 上没有，**手动做**（三行，比想象中的简单）：

**第 1 步**：本地读出公钥内容

```powershell
Get-Content ~/.ssh/id_ed25519.pub
```

会输出一行，形如：

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIIL95MkqjwHszrrZghUUGut+X4VW/tIvJvfGBa+8hXrJ 2421389161@qq.com
```

**整行复制**（从 `ssh-ed25519` 到最后）。

**第 2 步**：登录服务器（用密码），在服务器上执行

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo '刚才复制的那一整行公钥' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

> 权限说明：`~/.ssh` 必须是 700、`authorized_keys` 必须是 600，否则 sshd **会直接忽略**这个文件（这是 SSH 的安全设计，权限太松就等于谁都能改）。这一步忘了做是新手最常见的失败原因。

**第 3 步**：本地重新连接，验证

```powershell
ssh ubuntu@49.235.176.27
```

如果**不再提示输密码**直接进入，就成功了。

> 我上一轮做的事等价于：本地把公钥写进脚本，远程 `cat >> ~/.ssh/authorized_keys`。装完之后我后续所有操作都走密钥，不用再碰密码。

### 3.4 验证当前用的是哪种方式

```powershell
ssh -v ubuntu@49.235.176.27 exit 2>&1 | Select-String "Authenticated to"
```

输出 `Authenticated to ... using "publickey"` 就是密钥在生效。

### 3.5 （可选，进阶）禁用密码登录

确认密钥登录完全可用之后，可以关掉密码登录以彻底消除爆破风险：

```bash
sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
```

写入：

```text
PasswordAuthentication no
PermitRootLogin no
```

然后：

```bash
sudo systemctl restart ssh
```

> **警告：做这一步之前，务必在另一个终端确认密钥登录是好的**，否则可能把自己锁在服务器外面。学习期可以先不做，等熟练了再上。

## 4. 第三步：服务器初始化

这一步我用了 `bootstrap-server.sh` 一次跑完。手动做就是把下面 5 小节逐条敲一遍。

### 4.1 更新系统 + 装基础软件

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg git jq unzip
```

### 4.2 加 swap（**2C2G 必须做，不是可选**）

**为什么必须做**：这个项目构建 Next.js 前端时内存峰值会超过 2GB，物理内存不够就会被内核 OOM Killer 杀掉构建进程。**原作者当年就是因为这个，被迫把架构改成「本地构建镜像 → 推送到镜像仓库 → 服务器只拉不建」**（源码注释里写着 `v0.9.1: ECS 2C2G build OOM`）。我们加 3GB swap 就把这个问题从根上解决了。

```bash
sudo fallocate -l 3G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# 开机自动挂载
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 降低交换倾向（10 = 优先用物理内存，内存不够才用 swap）
sudo sysctl -w vm.swappiness=10
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf

# 验证：看到 Swap 那行不是 0
free -m
```

> 小知识：`vm.swappiness=10` 意思是「尽可能用物理内存，实在不够才换出」。服务器场景通常设 10（默认 60 太激进，会让活跃进程被换出、变慢）。

### 4.3 装 Docker（走腾讯云内网源，快很多）

```bash
# 1) 装 GPG 密钥
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://mirrors.cloud.tencent.com/docker-ce/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# 2) 加软件源（自动识别 Ubuntu 代号 jammy/noble）
CODENAME=$(. /etc/os-release && echo "$VERSION_CODENAME")
ARCH=$(dpkg --print-architecture)
echo "deb [arch=$ARCH signed-by=/etc/apt/keyrings/docker.gpg] https://mirrors.cloud.tencent.com/docker-ce/linux/ubuntu $CODENAME stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list

# 3) 安装
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 4) 验证
docker --version           # Docker version 29.8.1
docker compose version     # Docker Compose version v5.5.1
```

**为什么用 `docker-ce` 而不用 `docker.io`？** 官方仓库版本新、compose v2 插件完整；Ubuntu 自带的 `docker.io` 版本老、没有 compose 插件。

### 4.4 配镜像加速（大陆服务器必做）

**为什么**：Docker Hub (`registry-1.docker.io`) 在国内被 DNS 污染，不配加速连 `postgres:15-alpine` 都拉不下来。

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "registry-mirrors": [
    "https://mirror.ccs.tencentyun.com",
    "https://docker.m.daocloud.io",
    "https://docker.1panel.live"
  ],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "live-restore": true
}
EOF

sudo systemctl restart docker
sleep 3

# 验证：末尾能看到 registry-mirrors 那三个地址
docker info | grep -A3 "Registry Mirrors"
```

逐项解释：

| 配置 | 作用 |
|---|---|
| `registry-mirrors` | 第一个是腾讯云**内网**镜像站（免费、最快），后两个是公网备用 |
| `log-driver` + `max-size` | 容器日志最多 10MB × 3 份，**防止日志把磁盘写满** |
| `live-restore` | Docker 重启时容器不中断（升级 docker 时有用） |

> 本地 Windows 上我也做过同样的事（写 `C:\Users\<你>\.docker\daemon.json`），因为 Docker Desktop 用的也是这个文件。区别是本地第一个镜像用 `docker.m.daocloud.io`（没有腾讯云内网）。

### 4.5 建项目目录 + 加 docker 组

```bash
sudo usermod -aG docker ubuntu     # 让 ubuntu 用户能用 docker（不用每次 sudo）
sudo mkdir -p /opt/DecisionCourt
sudo chown -R ubuntu:ubuntu /opt/DecisionCourt

# 验证（需要重新登录才生效）
exit
```

重新 `ssh ubuntu@...` 进来后：

```bash
docker ps    # 不加 sudo 也能跑 = docker 组生效
id -nG ubuntu | tr ' ' '\n' | grep docker
```

## 5. 第四步：把代码放到服务器

两种方式，**推荐方式 A**。

### 方式 A：git clone（真实工作流，推荐）

前提：代码已经推到 GitHub（上一轮你在自己终端里推成功了，远程是 `git@github.com:to-resolve/DecisionCourt.git`）。

```bash
cd /opt/DecisionCourt
git clone git@github.com:to-resolve/DecisionCourt.git .
```

> 服务器上首次 git clone SSH 地址需要部署密钥。简单做法是用 HTTPS：
> ```bash
> git clone https://github.com/to-resolve/DecisionCourt.git .
> ```
> 私有仓库会要求输入 GitHub 用户名 + **Personal Access Token**（不是登录密码！在 GitHub → Settings → Developer settings → Personal access tokens 里生成，勾 `repo` 权限）。

**注意**：clone 下来的**没有 `.env`**（它在 gitignore 里），要手动创建，见 §6。

### 方式 B：scp 传压缩包（我上一轮用的）

为什么当时的代码用这个方式：GitHub push 卡在凭据窗口（非交互环境拿不到授权），但我不想让部署停在等授权上，所以先把本地打包传上去。

本地 PowerShell：

```powershell
cd E:\Code\DecisionCourt-new

# 1) 打包（排除不需要的目录）
tar -czf "$env:TEMP\dc_repo.tar.gz" `
  --exclude=./.git --exclude=./.workbuddy --exclude=./secrets `
  --exclude=./logs --exclude=node_modules --exclude=.next `
  --exclude=test-output .

# 2) 确认打包内容（关键：确认 .env 打包进去了、secrets 没进去）
tar -tzf "$env:TEMP\dc_repo.tar.gz" | Select-String "^\./\.env$"
tar -tzf "$env:TEMP\dc_repo.tar.gz" | Select-String "^\./secrets/"   # 应该没有输出

# 3) 上传
scp "$env:TEMP\dc_repo.tar.gz" ubuntu@49.235.176.27:/tmp/dc_repo.tar.gz
```

服务器上解压：

```bash
sudo mkdir -p /opt/DecisionCourt
sudo chown -R ubuntu:ubuntu /opt/DecisionCourt
tar -xzf /tmp/dc_repo.tar.gz -C /opt/DecisionCourt

# compose 需要写日志目录
mkdir -p /opt/DecisionCourt/logs/backend /opt/DecisionCourt/logs/caddy

# 确认关键文件都在
ls /opt/DecisionCourt/{docker-compose.yml,deploy/caddy/Caddyfile,.env}
```

> 为什么 `.env` 要打包进去但 `secrets/` 不要？`.env` 是应用的配置（里面有你本地开发用的 key，服务器上我会改掉敏感项）；`secrets/` 里是服务器的登录凭据，**绝不能上服务器**。

## 6. 第五步：配置 .env

`.env` 是整套部署的核心，服务器上的配置和本地开发有 5 处关键差异。

```bash
cd /opt/DecisionCourt
cp .env .env.bak        # 改之前先备份，出问题能回滚
nano .env
```

（`nano` 保存是 `Ctrl+O` 回车，退出是 `Ctrl+X`。）

| 项 | 本地开发值 | 服务器值 | 为什么 |
|---|---|---|---|
| `POSTGRES_PASSWORD` | `devpassword` | **服务器本地随机生成** | 生产不能用开发密码 |
| `DATABASE_URL` | `...@localhost:5432/...` | `...@postgres:5432/...` | 容器里的 `localhost` 指容器自己，连数据库要用**服务名** |
| `JWT_SECRET` | 本地那个 | **服务器本地随机生成** | 同上，且决定所有用户登录态 |
| `ALLOWED_ORIGINS` | `http://localhost,...` | `http://49.235.176.27:8080,...` | 后端 CORS 白名单，不匹配会直接拒请求 |
| `NEXT_PUBLIC_API_URL` | `http://localhost` | `http://49.235.176.27:8080` | **构建期变量**，前端代码里写死的地址 |
| `NEXT_PUBLIC_WS_URL` | `ws://localhost` | `ws://49.235.176.27:8080` | WebSocket 地址 |
| `DOMAIN` | `:80` | `:80` | Caddy 监听配置（`:80` = 监听 80 端口，不是域名） |
| `CADDY_HTTP_PORT` | （无） | `8080` | **新增**：把容器 80 映射到主机 8080，绕开备案扫描 |

生成随机密钥：

```bash
# 数据库密码：32 位
openssl rand -base64 32 | tr -d '/+=' | head -c 32

# JWT 密钥：更长的随机串
openssl rand -base64 48 | tr -d '\n'
```

把输出分别填进 `POSTGRES_PASSWORD` 和 `JWT_SECRET`，并**同步更新 `DATABASE_URL` 里的密码部分**（这三处必须一致，否则后端连不上库）。

最后收权限：

```bash
chmod 600 /opt/DecisionCourt/.env
```

> **重要认知**：`NEXT_PUBLIC_API_URL` 和 `SEARCH_PROVIDER` 的类型完全不同！
> - `NEXT_PUBLIC_*` 是**构建期变量**——`next build` 时就被编译进 JS 产物，改了必须 `--build` 重新构建
> - `SEARCH_PROVIDER` / `JWT_SECRET` 等是**运行时变量**——容器启动时读取，改了只要 `docker compose up -d` 重启容器
>
> 这就是为什么改 IP 相关的配置必须重新构建前端。

## 7. 第六步：构建启动

```bash
cd /opt/DecisionCourt

# 直接跑（前台，会看到实时输出）
docker compose up -d --build
```

**如果 SSH 会话可能中断**（比如网络抖动），用后台方式跑，输出写日志：

```bash
nohup docker compose up -d --build > /tmp/dc_build.log 2>&1 &
```

然后另开一个连接看进度：

```bash
tail -f /tmp/dc_build.log
```

（`tail -f` 是实时跟踪，`Ctrl+C` 退出跟踪但**不会**停掉后台构建。）

**构建要多久**：2C2G 加 swap 大约 **8-15 分钟**。会依次看到：

1. 拉基础镜像（golang / node / postgres / redis / caddy）—— 走镜像加速，1-2 分钟
2. backend：`go mod download`（走 goproxy.cn）→ `go build`
3. frontend：`pnpm install`（走 npmmirror）→ `next build`（**最吃内存，最慢的一步**）
4. 组装镜像 → 启动 5 个容器

**构建期间看内存**（另开一个终端）：

## 14. 增量部署的 4 个坑（本轮全部实际踩到）

| # | 坑 | 现象 | 正解 |
|---|---|---|---|
| 1 | **`docker compose up -d` 不重启 Caddy** | Caddyfile 明明改了，容器日志还报旧配置的错 | Caddyfile 是 **bind mount**，compose 只比对 service 定义、**不比对挂载文件内容**。改完必须 `docker compose restart caddy` |

| 4 | **传了本地 `.env`** | 生产密钥被开发配置顶掉，无法恢复 | 打包：`--exclude=./.env`；部署后 `md5sum` 比对证明没动 |

## 16. 本项目特有的坑：前端 lint 会阻断 `next build`

v2.6 的前端**跑不通 production build**，因为死代码触发了 error 级 lint：

- `frontend/.eslintrc.json` 把 `@typescript-eslint/no-unused-vars` 配成 **`"error"`**
- `frontend/next.config.mjs` **没有** `eslint: { ignoreDuringBuilds: true }`
- → `next build` 会跑 ESLint，撞到 error 直接中断

本轮清了 **7 处**：`storedEvidences`、`setAgents`、`addEvidence`（×2）、`setBeliefDiffs`、`getStoredEvidences`、`setMemoryEntries`，以及 WS `useEffect` 里一个**只赋值不读取、早已失效的 `let mounted` 守卫**（`mounted = false` 在 cleanup 里写，但没有任何 handler 读它）。

判断这类问题时的经验：

```bash
# 1) 先确认 lint 是不是 error 级（决定 next build 会不会挂）
cat frontend/.eslintrc.json | grep -A3 no-unused-vars
# 2) 再确认 next.config 有没有关掉构建期 lint
grep -n "ignoreDuringBuilds" frontend/next.config.mjs
# 3) 不要盲删，先跑一次 build 让 lint 报全清单
docker compose up -d --build 2>&1 | grep -i "no-unused-vars"
```

**踩坑点**：ESLint 一次**不会**报全，改完一批才会露出下一批（本轮第一次报 5 处，重跑又报 3 处）。所以要"改一批 → 重跑 → 再改"，别以为一轮就干净。

**删变量时注意**：只删**解构变量**，不要动 store 里的成员和接口定义。像 `CourtroomHydrateActions` 接口里的 `addEvidence` / `getStoredEvidences` 两个调用方还在用，删了接口就编译不过——只把当前作用域里没用到的那几个名字从解构里摘掉即可。

## 17. 只有真实浏览器才能发现的 3 个坑（2026-09-21 二次排查）

v2.6 上线后点「立案 · 开庭」报 403，修完又冒出 TypeError。这三个坑**服务端 curl
一个都测不出来** —— 我前三轮 curl 探测全部给出了误导性结论，最后靠真实浏览器才定位。

### 17.1 CSRF cookie 的 Path 太窄 → `document.cookie` 读不到

现象：`POST /api/v1/courtrooms` → 403 `{"code":"CSRF_TOKEN_MISMATCH"}`。
注意 **403 不是 401**：401 是鉴权问题，403 是授权/CSRF/CORS 问题 —— 这个区分是排查起点。

根因（容易反直觉）：

> **RFC 6265 §5.4**：`document.cookie` 只暴露 path 能匹配**当前文档 URL** 的 cookie；
> 而 `Set-Cookie` 的 path 匹配的是**请求 URL**。两者是不同的匹配对象。

`XSRF-TOKEN` 的 Path 被设成 `/api/v1`，而页面在 `/`，于是：

```
document.cookie      →  ""      （前端读不到 token，不带 X-XSRF-TOKEN 头）
POST /api/v1/xxx     →  浏览器照样带 cookie（请求 URL 匹配上了）
                     →  后端见 cookie 有、header 空 → 403
```

**cookie 一直在链路上传，只有 JS 看不见** —— 这就是它难猜的原因。

**规则：凡是需要前端 JS 读取的 cookie，`Path` 必须是 `/`。**

### 17.2 `crypto.randomUUID()` 在纯 HTTP 部署下不存在

`http://<IP>:8080` **不是安全上下文**（安全上下文 = HTTPS 或 localhost）：

```
window.isSecureContext   →  false
typeof crypto.randomUUID →  "undefined"
```

| 后果 | 说明 |
|---|---|
| 点「开庭」抛 `TypeError: crypto.randomUUID is not a function` | 请求根本没发出去，后端日志里什么都看不到 |
| 所有访客共用同一个匿名身份 | 代码写了 `if (!crypto.randomUUID) return "anon_placeholder"` 兜底 → **互相能看到对方创建的庭审** |

⚠️ **本地 `localhost` 是安全上下文，所以这两个问题在本地完全复现不出来**，
必须打公网地址测。

**规则**：
- `crypto.getRandomValues()` **不要求**安全上下文，用它兜底即可（仍是 CSPRNG）
- **绝不用「返回固定值」当兜底** —— 会把功能问题静默升级成隐私缺陷

### 17.3 怎么验：复用系统 Chrome，别下载 Chromium

`agent-browser install` 要下 ~500MB 浏览器。用 `puppeteer-core` + 本机已装的 Chrome
只要 25 个小包、几秒钟：

```bash
npm install puppeteer-core --registry=https://registry.npmmirror.com
# executablePath: "C:\\Program Files\\Google\\Chrome\\Application\\chrome.exe"
```

一次能拿到全套证据：

```js
page.on("pageerror", e => ...)          // 控制台报错（TypeError 等）
page.on("response", ...)                // 每个 API 的状态码 + 响应体 + 请求头带没带某 header
await page.evaluate(() => document.cookie)          // 前端 JS 能看到什么
await page.evaluate(() => window.isSecureContext)   // 安全上下文判定
const cdp = await page.target().createCDPSession(); // 浏览器实际持有什么 cookie
await cdp.send("Network.enable");
(await cdp.send("Network.getAllCookies")).cookies   // 含 document.cookie 看不到的
```

**注意**：不要 `cat` cookie jar 或打印 token 值 —— 会把 JWT 写进日志。
只输出长度、md5、属性名。

> 本项目由此定位到：`document.cookie` 为空但浏览器实际持有 3 个 cookie（含
> `XSRF-TOKEN path=/api/v1`）—— 这条证据直接坐实了 17.1。

### 17.4 顺带发现：纯 HTTP 部署还有这些限制

`crypto.subtle` 不可用、Service Worker 受限、剪贴板 API 受限、浏览器显示"不安全"。
学习/演示能忍，**真要给人用就上域名 + HTTPS**（香港/新加坡节点免备案）。

## 18. 本轮第二个独立缺陷（也修了）

「立案」表单把选项 A/B 标注为 **「选填 · 不填将由 Agent 协助生成」**，但：

## 19. 第四个坑：埋在"两个 fetch"里的 CSRF（2026-09-21 三轮排查）

前三个坑修完后（§17 的 cookie Path、§17 的非安全上下文、§18 的表单契约），用真实浏览器走完整流程：

```
POST /api/v1/courtrooms               -> 200   立案成功
POST /api/v1/courtrooms/<uuid>/start  -> 200   开庭成功
庭审状态机 idle -> opening -> 开庭陈述结束      业务正常
POST /api/v1/courtrooms/<uuid>/events -> 403 {"code":"CSRF_TOKEN_MISMATCH"}   × 15+ 次
```

主流程都通了，只剩埋点这条**旁路**在报错。这种"主流程正常 + 旁路报错"最容易看漏。

### 19.1 根因：自定义 fetch 有第二个

CSRF 是 v2.5 引入的，改法是在 `lib/api.ts` 的 `fetchJson` 里注入 `X-XSRF-TOKEN`。
但前端 `lib/transport.ts`（埋点上报）**有自己独立的 fetch**，之前 v0.10.1 还专门修过一次它漏带 `Authorization`：

```ts
const authHeaders: Record<string, string> = { ...headers };
if (token) authHeaders["Authorization"] = `Bearer ${token}`;   // 抄了鉴权
// CSRF header 没抄 —— v2.5 加 CSRF 时只改了 api.ts
```

所以那条链路是：**v0.10.1 修好 401，v2.5 又漏出 403**。修一次漏一次，因为"要带哪些 header"这件事抄了两份。

**怎么快速判断有没有同类问题**（比读代码可靠）：

```bash
# 列出所有自己造 fetch 的地方，逐个看是否带 CSRF
grep -rn "fetch(" frontend/lib frontend/app frontend/components --include=*.ts --include=*.tsx \
  | grep -v "fetchJson\|csrfHeaders"
```

### 19.2 修法：收敛成单一入口，不抄第二遍

新增 `frontend/lib/csrf.ts`（`readCookie` / `isStateChanging` / `csrfHeaders` + 两个常量），
`api.ts` 与 `transport.ts` 都改成一行：

```ts
Object.assign(headers, csrfHeaders(method));
```

**关键原则：只要"哪些请求要带某个 header"存在于两个地方，就一定会漂移。
正确做法是收敛成单一入口，而不是"这次把两处都改对"。**

### 19.3 为什么**没有**在后端把 `/events` 改成 CSRF 豁免

那是写库的状态变更请求，豁免等于开一个 CSRF 缺口——第三方站点可以伪造埋点污染
`decision_events` 表。**修前端漏带 header，不要降级后端校验。**

### 19.4 教训：注入 fake 的测试测不出"真实实现漏了什么"

`transport.test.ts` 原有 12 项全部用**注入的 fake fetcher**，只验证"传进去的 header 被透传"，
**永远测不到 fetcher 自己漏带了 header**。这就是这个 bug 能穿过 105 项既有测试上线的原因。

新增的 `lib/csrf.test.ts` 第 2 层直接跑 `defaultDeps().fetcher`（真实生产实现），打桩
`window`/`document`/`localStorage`/`fetch` 后断言**实际发出的 header**。并做了变异验证：
把修复注释掉 → 该测试立即 FAIL；恢复 → 12/12 通过。

> **要断言"我确实带上了某个 header / 某个配置"，就必须测真实实现，不能测 fake 的透传。**

## 20. CI 自己也需要被检查（同一轮发现的两个缺陷）

`test.yml` 有两个问题，**都属于"看板上是绿的，但其实什么都没跑"**：

### 20.1 `Doc cross-links` 漏写 job ID → 重复 key

```yaml
  # ============== Doc cross-links ==============
    name: Doc cross-links      # ← 4 空格缩进，但没有 `  doc-links:`
    runs-on: ubuntu-latest
    steps: ...
```

**YAML 里注释不改变缩进层级**，这三行被并进上一个 job `dep-audit` 的 mapping，
与它已有的 `name`/`runs-on`/`steps` 重复定义。后果二选一：

1. 解析报 duplicate key → **整个 workflow 失效，CI 全不跑**
2. 解析器 last-wins → `dep-audit` 的 `steps` 被覆盖，**`govulncheck` + `pnpm audit` 静默不执行**，
   而这个 job 依然叫 "Dependency audit"、依然显示绿色

**实际命中的是第 1 种。** 用 GitHub API 查 push 后每次 Test 运行，特征完全一致：

```bash
curl -s "https://api.github.com/repos/to-resolve/DecisionCourt/actions/runs?per_page=10"
curl -s "https://api.github.com/repos/to-resolve/DecisionCourt/actions/runs/<id>"     # name / created_at / updated_at
curl -s "https://api.github.com/repos/to-resolve/DecisionCourt/actions/runs/<id>/jobs"
```

```
name: ".github/workflows/test.yml"    ← 不是 "Test"，回落到文件路径
created_at == updated_at              ← 0 秒瞬时失败
jobs: total_count = 0                 ← 一个 job 都没有
check-runs: total_count = 0           ← 连 check 都没注册
```

**「name 回落成文件路径 + 0 job + 瞬时失败」= GitHub 判定 workflow 文件无效的确切签名。**
即：这个 workflow 自那次改动起**一个 job 都没跑过**，而每次 push 只留下一条没有内容的红色记录。

修好（补上 `  doc-links:`）后，同一次 push 立刻变成 `name: Test`、`jobs: total_count = 4`，
`Doc cross-links` 首次作为独立 job 出现。**4 个空格的缩进，代价是整条 CI。**

**自查脚本**（20 行，扫"同一个 job 下重复的 4 空格 key"）：

```js
// 核心思路：遇到 `  jobid:` 开新 job；遇到 `    key:` 记进当前 job 的 key 集合；
// 同一个 job 里 key 重复出现 → 报告行号
```

### 20.1b 附带发现：两个 job 的 `pnpm install` 都失败（**尚未修复**）

workflow 结构修好后，第一次"真的跑起来"立刻暴露：

| job | 失败步骤 | 被跳过的步骤 |
|---|---|---|
| `Frontend (Next.js)` | `Install dependencies`（`pnpm install`） | `Type check` / `Unit tests` / `Build` |
| `Dependency audit` | `pnpm install (frozen lockfile)` | `pnpm audit (high+)` |

已排除：锁文件与 `package.json` 不一致（逐项对比 `importers['.']` → 完全一致）、
CI 的 pnpm 9 与本地 pnpm 11 版本偏斜（`pnpm@9.15.9 install --frozen-lockfile --lockfile-only` → 1 秒通过）。
所以故障在**真实下载/安装阶段**，需要 CI 日志正文才能定位（`/actions/jobs/<id>/logs` 要鉴权，
公开仓库也拿不到，得在网页上点开或配 GH token）。

> 教训：**"从没跑过"和"跑了但失败"是两种完全不同的状态，而它们的界面表现都是红色。**
> 排查 CI 时第一件事应该是确认"这次运行到底有几个 job"，而不是直接看红绿。

### 20.2 前端测试是硬编码文件清单 → 新护栏从来不跑

原本只列了 4 个文件：

```yaml
pnpm exec node --experimental-strip-types --test \
  lib/transport.test.ts \
  lib/reconnect.test.ts \
  lib/analytics/analytics.test.ts \
  lib/analytics/runtime.test.ts
```

于是 `lib/auth.test.ts`、`lib/random.test.ts`（§17 的护栏）和 `lib/csrf.test.ts`（§19 的护栏）
**在 CI 里一次都没跑过**。§17 当时写"全量前端测试 105 项通过"是**本地**的数字，CI 只跑了 4 个文件。

改 glob（**引号必须保留**，交给 Node 自己展开 `**`；否则 shell 的 globstar 默认关闭，
`**` 退化成 `*`，会漏掉 `lib/analytics` 这类子目录——本机实测差 31 项）：

```yaml
pnpm exec node --experimental-strip-types --test "lib/**/*.test.ts"
```

`frontend/package.json` 的 `test` 脚本同理：原 `$(find lib -name '*.test.ts')` 依赖 POSIX shell，
**Windows 上 npm 用 cmd 执行 `scripts`，本地 `npm test` 直接失败**。改成同一个 glob 后跨平台一致。

> **教训：写了护栏 ≠ 护栏生效。** 硬编码的测试清单没有任何机制提醒你"新增的文件没进来"，
> 它会静默过期。用 glob / discovery，并且**偶尔确认一下 CI 真的执行了这些文件**。
