## 1. 业务痛点

### 1.1 现状
- baseRules 写在 `internal/agent/prompts.go` 第16-77 行（共约 60 行字符串字面量）
- 任何 prompt 调整都要：改代码 → `go build` → `docker build` → `docker compose up` → 完整链路重测
- 一次"改 2 个字试效果"的迭代周期：**约 30 分钟**
- 没有版本对比，git history 是唯一审计 trail
- 没有"对同一输入，不同 prompt 版本输出差异"的量化评估

### 1.2 目标（v1.0.3 落地后）
- 改 prompt：**秒级热加载**（YAML 文件 mtime 检测）
- 版本对比：**1 个 REST 调用**跑 LLM-as-judge eval
- A/B Test：**2 个版本同时跑 trial**，自动评分选赢家
- 评估自动化：3 个内置 eval rules（length / evidence_id_format / stance_mention）

### 2.2 YAML Schema

```yaml
# backend/prompts/base.yaml
version: "1.0.3-pr1"      # semver + git_sha 标识
git_sha: ""               # 自动注入 build-time
created_at: "2026-08-20"  # 自动注入
author: "Exist"           # 可选, prompt 修改者

base_rules: |
  你是一名专业的决策顾问...
  1. 每次发言最多 300 字...
  16. v1.0.2 候选 4 已反驳证据集合跟踪 (PRD §4.3.3)...

prosecutor_role: |
  你是"选项A代表"...

defender_role: |
  你是"选项B代表"...

investigator_role: |
  你是"调查员"...

clerk_role: |
  你是"中立的书记员"...

# A/B Test 支持多版本并存
versions:
  v1_0_3_pr1:
    file: "base.yaml"  # 指向上面 base_rules
    status: "active"
  v1_0_4_pr1:
    file: "versions/v1.0.4-pr1.yaml"
    status: "experimental"
```

### 2.3 Go API 设计

```go
// backend/internal/promptlab/loader.go

package promptlab

// Store 提供 baseRules 的 thread-safe 访问 + 热重载.
type Store struct {
    mu       sync.RWMutex
    version  Version
    rules    map[string]string  // "base_rules", "prosecutor_role", ...
    yamlPath string
    lastLoad time.Time
}

func NewStore(yamlPath string) (*Store, error)

// Load (re)reads the YAML file. mtime > lastLoad → reload.
// 检测文件热更新, 触发 reload.
func (s *Store) Load() error

// GetBaseRules returns the current base_rules string + version.
func (s *Store) GetBaseRules(toolsBlock string) string

// GetRole returns prosecutor_role / defender_role / etc.
func (s *Store) GetRole(role string) string

// Version returns the current loaded version metadata.
func (s *Store) Version() Version
```

### 2.4 LLM-as-judge Eval

```go
// backend/internal/promptlab/eval.go

package promptlab

type EvalRule string

const (
    EvalRuleLength          EvalRule = "length_compliance"        // ≤ 300 字
    EvalRuleEvidenceID      EvalRule = "evidence_id_format"      // evidence_refs 是合法 E00X
    EvalRuleStanceMention    EvalRule = "stance_mention"          // 含立场关键词 (pro_a/pro_b/challenge/neutral)
    // 后续可加: EvalRuleBeliefConsistency, EvalRuleRebuttalAvoid, ...
)

type EvalResult struct {
    Rule      EvalRule
    Score     float64       // 0-1
    Pass      bool         // score > 0.7
    Reasoning string        // LLM judge 给的理由
    LatencyMs int
}

func Eval(llm LLM, rule EvalRule, output string) (EvalResult, error)
```

**Eval 实现**：用同一个 LLM 客户端（DeepSeek v4）做二次判定，温度 0.2（与 v0.10.24 stance judge 同），prompt：
```
你是 [rule_name] judge。判定下面这段发言是否合规：
规则：[rule_definition]
发言：[output]
返回严格 JSON {"score": 0-1, "pass": true/false, "reason": "≤50字"}
```

### 2.5 A/B Test

```go
// backend/internal/promptlab/abtest.go

type ABTestResult struct {
    VersionA  string                     // "1.0.3-pr1"
    VersionB  string                     // "1.0.4-pr1"
    ScoresA   map[EvalRule]float64        // {length: 0.9, evidence_id: 0.8, ...}
    ScoresB   map[EvalRule]float64
    Winner    string                     // "A" / "B" / "tie"
    Confidence float64                    // 0-1, judge confidence
    Reasoning string
}

func RunABTest(
    llm LLM,
    versionA, versionB string,
    rule EvalRule,
    trialOutputs []string,              // 同一输入的 A/B 输出
) (*ABTestResult, error)
```

**A/B Test 实现**：对每个 trial output，分别 eval A/B 各 rule，然后求平均 score 比较。

### 2.6 REST API

```
POST /api/v1/prompts/eval
Body: { "rule": "length_compliance", "llm_output": "..." }
Resp: { "code": 0, "data": EvalResult }

POST /api/v1/prompts/abtest
Body: {
  "version_a": "1.0.3-pr1",
  "version_b": "1.0.4-pr1",
  "rule": "length_compliance",
  "trial_outputs": ["output1", "output2", ...]
}
Resp: { "code": 0, "data": ABTestResult }

GET /api/v1/prompts/version
Resp: { "code": 0, "data": Version }

POST /api/v1/prompts/reload  # 触发热加载 (admin only)
Resp: { "code": 0, "data": { "loaded_version": "...", "at": "..." } }
```

## 6. 风险与缓解（2026-08-21 更新）

| 风险 | 影响 | 缓解 | 状态 |
|---|---|---|---|
| YAML 加载失败 → baseRules 为空 | 庭审输出混乱 | fallback 到 hardcoded 字符串（PR-B1 必备） | ✅ PR-B1 已落地 |

| YAML 文件被误改 | 庭审全部坏掉 | git pre-commit hook 检查（后续 PR） | ⏸ 待补 |
| Dev compose 启动配置脆弱（DATABASE_URL 拼接 / NEXT_PUBLIC_* 覆盖 / Windows npipe）| Windows / Linux 切换困难 | `eef932e` + `bea7289` + `1eb037f` + `29daff0` 修复（PR-B1 启动验证时发现） | ✅ 已修 |
| React_runner 流式解析 silent error | 庭审记录全空但不报错 | D2 fix `694a89e` 加 WARN 日志 + saveAgentMessage 拦截空 content | ✅ 已修 |
| Direct_verdict fallback "共 0 轮" | 用户看到错误轮数 | D3 fix `694a89e` transitionPhase(closing, round) + maxRound(messages) | ✅ 已修 |
| ArgumentMap 类 UI 组件"用户根本不会看" | 浪费开发资源 | ADR 0032 + `16332aa` 删除 ArgumentMap + 卸 `reactflow` 依赖 | ✅ 已删 |
