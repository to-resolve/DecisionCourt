## 🐛 实施过程中的 bug / 教训

### B.1 PR-B: 截断函数中文 UTF-8 半字符问题

**症状**: 第一版 `truncate(s, max)` 用 `len(s) <= max` 字节判断, 对中文会把一个 3-byte UTF-8 字符切到 1-2 字节, 产生乱码。

**根因**: `len(string)` 返回字节数, 不是 rune 数。

**修复**: 新增 `truncateRunes(s, maxRunes)` 用 `utf8.RuneCountInString + []rune` 转换。

**学习**: 中文项目永远不要用 `len(string)` 做长度限制, 必用 `utf8.RuneCountInString`。

### B.2 PR-C: viper 1.21.0 lowercase bug 30+ env 残留

**症状**: v0.10.19 修过 5 个关键 env, 但生产环境发现 33 个 env 仍走 `AutomaticEnv` lowercase 路径, 全部 silent fail (拿 SetDefault 默认值)。

**根因**: viper 1.21.0 `AutomaticEnv()` 默认 lowercase env key, `BindEnv(key, envName)` 第二个参数才能绕过 — 但需每个 env 单独列。

**修复**: 抛弃 viper env lookup, 改用 `os.Getenv` 走 `envOrDefault` helper。helper 第二参数当默认值, go code 就文档。

**学习**: silent fail 修复要"全栈扫一遍", v0.10.19 修了 5 个关键 env 但没意识到剩余 33 个也需要修。

### B.3 教训: helper 第二参数当默认值"代码即文档"

viper `SetDefault` 把默认值藏在 viper 内部 store, 看代码不直观, 还存在 silent fail 陷阱。`envOrDefault(key, defaultVal)` 把默认值作为函数参数, **代码就文档** — 看到 helper 调用就知道默认值是什么, 不用 grep viper.SetDefault。

### B.4 教训: fail-fast 不散落到 helper

曾考虑让 `envOrDefault("JWT_SECRET", "")` 缺失时 panic, 但那样 fail-fast 散落到 33 处, 难维护。集中在 `Load()` 末尾 `mustEnvs` 显式 fail-fast, 可读性 + 排查友好。

### B.5 教训: PR-B 文档/代码分裂修复

v0.10.17 之前: `prompts.go` 写 200 字, 但 PRD/roadmap/README 都写 300 字 — 文档/代码分裂。本次 PR-B 顺手对齐 3 处文档。教训: **任何"硬规则"必须有 prompt 软约束 + 后端硬截断 + 文档口径 三层一致**。

### B.6 教训: v0.10.20 状态行错位 24 天 (历史教训)

[以前 release notes 反思提到](v0.10.20.md#-反思2026-08-05-retrospective): v0.10.18 / v0.10.20 状态行写"🟡 部署中" / "🟡 准备发版"长达 24 天未更新 → 文档说"准备发版"而实际"已部署"。

**本 release notes 修正**: v0.10.21 没有 ECS 部署目标 (2026-08-05 ECS 终止), 状态行写"✅ 已合并到 main (本地部署模式)", 不写"待 push"或"准备发版"。提前规避 24 天错位。

## 📝 反思

**v0.10.21 = 「硬化」主题, 0 触及裁决**

按用户偏好「上一阶段完全收尾 > 下一阶段开发」(2026-08-05 决策), v0.10.21 主题刻意避开裁决逻辑 (LLM-as-judge / 反驳证据 / 新意度检查), 纯硬化 + 收尾。教训: **当项目处于"硬规则未对齐"状态时, 优先做硬化 (低成本 + 高信息密度), 再做裁决 (高风险 + 需讨论)**。

**2 个 PR 各自的边界**

- **PR-B**: 改动 react_runner 出口, 加 Speaker 字段, 风险低 (纯截断 + 字符数限制, 客观规则)
- **PR-C**: 改动 Load() 主体, 删 viper 4 处调用, 风险中 (波及 33 env 行为变更, 但都是 silent fail 修复不是语义变更)

**silent fail 修复 vs 语义变更**

PR-C 边界的核心区分: **修复 silent fail 是行为变更, 但不是语义变更**。修改前: `.env` 设 `LLM_MODEL_V3=X` 代码读到 default `deepseek-chat` (错)。修改后: 代码读到 `X` (对)。两个都是合法行为, 选"对的那个"是从 silent fail 修复。

**为什么不写 v0.10.21 release notes 在 PR-C 落地时立即写**

v0.10.20 反思提到: "发布流程的最后一步是 git push tag, 但 push 完没有强制要求回写 release notes 状态 → 文档说'准备发版'而实际'已部署'长达 24 天"。本次 v0.10.21 没 tag (本地模式), 但 5 commits 落地后立即写 release notes, 避免重蹈覆辙。
