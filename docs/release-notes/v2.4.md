## 🆕 新增功能（v2.4 commit 汇总）

### P1-7: APP_ENV + prod 启动 fail-fast

**新增 `Config.AppEnv` 字段**（`backend/internal/config/config.go`）：
- env 读取：`envOrDefaultString("APP_ENV", "dev")`（dev 默认，本地开发模式 fall-back）
- 5 个辅助方法：`IsDev() / IsProd() / IsStaging() / IsProdLike() / ValidateAppEnv()`
- `ValidateAppEnv()`：dev/staging/prod 之外的拼写错误（如 `Production` / `stage`）→ fail-fast 拒绝启动

**main.go 启动 fail-fast**（`backend/cmd/server/main.go`）：
- 新增 `enforceProdInvariants()` 函数，仅 `APP_ENV=prod|staging` 时触发
- 4 条 invariant 检查：
  1. `ALLOWED_ORIGINS` 不含 `localhost` / `127.0.0.1`（dev fallback）
  2. `COOKIE_SECURE` 必须 `true`
  3. `JWT_SECRET` 长度 ≥ 32（避免 dev 默认 weak secret）
  4. `LLM_API_KEY` 非空

**配置示例**（`backend/.env`）：
```bash
# dev 模式（默认，无需设置）
# APP_ENV=dev

# 生产部署必须显式：
APP_ENV=prod
ALLOWED_ORIGINS=https://yourdomain.com   # 不含 localhost / 127.0.0.1
COOKIE_SECURE=true
JWT_SECRET=<≥ 32 字符的强 secret>
LLM_API_KEY=sk-...
```

### P1-5: UserFacingError.WithDetail prod 守卫

**修改 `errors.go:194-197`**：
```go
func (e UserFacingError) WithDetail(detail string) UserFacingError {
    if config.AppConfig.IsDev() {
        e.Detail = detail
    }
    // prod|staging → 静默丢弃（不进 wire）
    return e
}
```

**修复的承诺**：`errors.go:84` 注释 "Detail 字段仅 dev 模式填充;prod 留空" 此前**注释承诺 vs 代码未做**，本次让代码与注释对齐。

**5 个 err 分支全覆盖**：`ClassifyError` 内 5 处 `WithDetail(err.Error())`（concurrency / react_max_iter / budget / state_machine / unknown）prod 模式全清空。

### P1-3: WebSocket 输入长度校验

**新增常量**（`backend/internal/api/websocket.go`）：
- `wsMaxMessageBytes = 64 * 1024`（单条 WS 消息最大字节数）
- `wsMaxContentChars = 4096`（与 HTTP `SubmitEvidence.content max=4096` 对齐）
- `wsMaxInterruptChars = 4096`（与 HTTP max 对齐）

**3 处修改**：
1. 升级后立即 `conn.SetReadLimit(wsMaxMessageBytes)`
2. `submit_evidence` handler：`len(content) > wsMaxContentChars` → 广播 `ClassUserInput + CodeActionFailed` UFE
3. `interrupt` handler：`len(content) > wsMaxInterruptChars` → 同上

**前端体验**：超长 content 时前端 Toast 提示"证据内容超长（最大 4096 字符）"，不会静默丢弃。

## 📝 反思

### 触及 §2.1 裁决逻辑：**0**

v2.4 全部改动都是防御性 / 校验类，**不动审判逻辑**。

### v2.4 教训

1. **"注释承诺 vs 代码未做"是技术债典型反模式** —— P1-5 修了 0.5 天就完事，但文档与代码脱节 24+ 天没人发现。建议每月扫一次 `// TODO` / `// XXX 注释承诺` 这种"代码注释里画大饼但没实现"的债。
2. **fail-fast 是 prod 唯一防线** —— P1-7 不需要复杂 CI 校验，main.go 启动 4 条 invariant 已经能拦住 90% 误部署。
3. **WS 路径绕过 HTTP binding 是经典坑** —— P1-3 修了 0.5 天但绕过的攻击面极大。建议未来所有 WS handler 路径都要显式 length check。
4. **构造器注入模式推广到 config** —— `Config.AppEnv` 是 P1-5 和 P1-7 共享的开关，放进 config 包统一管理比散在多个文件更可维护。

### AGENTS.md §11 实践验证

v2.4 全部走完 `go test ./...`（24 包 PASS）后才 push，符合 §11.5 checklist "业务端点健康检查"。无 dev compose 实操（变更不涉及运行时路径），符合 §11.4 例外 "纯函数 / 类型 / 接口定义"。
