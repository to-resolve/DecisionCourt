## 🎯 核心主题

**为 DecisionCourt Agent 落地"新意度 Jaccard 强制换角度"硬规则：与同 agent 历史发言 Jaccard > 0.6 触发 retry hint 强制 LLM 换角度，2 次 retry 失败 fallback 返回带 NoveltyRejected=true 的 Speaker。Agent 重复发言从"靠 Prompt 自约束"升级为"后端硬校验 + 自动 retry"。**

3 个核心收益:
1. **PRD §4.3.3 落地** — 新意度检查从 ⏳ v0.7+ 计划 → ✅ v0.10.23 候选 2
2. **Jaccard 框架共享** — bagOfWords + JaccardSimilarity 抽到 `internal/util/bagofwords.go`，让 `belief.convergence.go` 与 `agent/react_runner.go` 算出同一 jaccard（避免不同实现导致 §2.1 裁决不一致）
3. **架构解耦** — Orchestrator 不直接依赖 DB，通过 `HistoryProvider` 接口让 service 层注入历史发言查询逻辑

## 🐛 实施过程中的 bug / 教训

### D.1 抽 bagOfWords 到 util 时漏改 belief 测试

**症状**: 抽 `bagOfWords` 到 util 包后，`internal/belief/convergence_test.go:201-202` 还引用包内私有 `bagOfWords`，编译失败。

**根因**: `grep "bagOfWords"` 漏检包内 test 文件。

**修复**: 删除 `TestBagOfWords_ChineseAndEnglish`（已搬到 util 包 `TestBagOfWords_MixedCJKAndLatin`）。

**学习**: 抽公共代码时, **用 `grep -rn`** 跨所有包（含 test 文件）找所有引用, 不仅 production code。

### D.2 Orchestrator 不直接依赖 DB — 抽象 HistoryProvider

**症状**: Orchestrator struct 没 DB 字段，但需要拉同 agent 历史发言。

**根因**: Orchestrator 设计时只接 `llm.Client / a2a.Bus / memoryRepo / weakenRepo / evidenceLkp`，不含 DB。

**修复**: 新增 `HistoryProvider` interface + `SetHistoryProvider` 注入方法，让 service 层实现 `LoadAgentHistory` 并自注入到 orchestrator。

**学习**: 抽象边界用 interface 而不是直接接 DB，更解耦。Orchestrator 不需要知道 DB schema，service 知道。

### D.3 Service 自身实现 HistoryProvider 接口 — 自注入

**现象**: `service.LoadAgentHistory` 实现 `agent.HistoryProvider` 接口，`NewService` 之后调 `InjectHistoryProvider()` 把 service 注入到自己。

**好处**: 不引入新类型，service 既是 HistoryProvider 实现方，也是注入方。

**风险**: 自注入循环。Orchestrator 调 service.LoadAgentHistory，service 不调 orchestrator，**无循环**。

**学习**: 自注入只在调用图无环时安全。

### D.4 文档错位风险 — bagOfWords 已实现一次但只在 belief 包

**症状**: belief 包内 `bagOfWords` 完整实现，但 agent 包没复用，新写一遍可能实现不同（中文切词规则差异）。

**教训**: **抽公共代码时考虑"避免分裂实现"**。本次直接抽到 util 包避免类似问题。

### D.5 文档 vs 代码 §2.1 触及程度

| 改动 | §2.1 触及 | 备注 |
|---|---|---|
| `bagOfWords + JaccardSimilarity` | 0 | 纯数学算法 |
| `applySpeakerNoveltyCheck` | 轻度（阈值 0.6 客观） | PRD 已规定 |
| `applySpeakerNoveltyRetryLoop` | **轻度**（retry 行为是用户拍板） | 用户授权 2 次 retry + fallback |
| `LoadAgentHistory` | 0 | 纯 SQL 查询 |
| 前端 chip 显示 | 0 | 纯渲染 |

**§2.1 决策记录**: Jaccard > 0.6 阈值是客观数学 (PRD §4.3.3 已规定)，retry 行为 + fallback 策略是用户拍板的"2 次 retry + fallback"。本次按用户授权实装, 不重新讨论。

## 📝 反思

**v0.10.23 是 "硬规则化" 主题**

按用户偏好「按原 roadmap 推进, 不调整」, v0.10.23 候选 2 新意度检查从 roadmap §5.3 第二阶段第 2 项 ⏳ → ✅。与 v0.10.21 PR-B (发言长度硬截断) 同主题: **把"靠 Prompt 自约束"升级为"后端硬校验 + 自动 retry"**。

教训: **"硬规则化"是安全 LLM 的有效手段**:
- v0.10.21 PR-B: 发言长度 300 字硬截断 (后端兜底, 不让 LLM 输出 600+ 字)
- v0.10.23 候选 2: 新意度 Jaccard > 0.6 retry (后端兜底, 不让 LLM 重复自己)
- 共同模式: Prompt 软约束 + 后端硬校验 + 透明审计 (Speaker flag + 前端 chip)

**Jaccard 框架抽到 util 包 — 避免分裂实现**

之前 `bagOfWords` 在 belief 包内, agent 包本次需要, 直接抽到 util 包让两边共享。如果不抽, agent 包重写一份可能中文切词规则不同, 算出的 jaccard 也不同, 破坏 §2.1 裁决一致性。

教训: **公共 token 化 / Jaccard 算法应该跨包共享, 不在多个包里重复实现**。

**HistoryProvider 抽象 — 不让 Orchestrator 直接接 DB**

Orchestrator 不直接接 DB, 通过 `HistoryProvider` interface 让 service 注入。这是 v0.5+ 一贯的"接口隔离"设计: Orchestrator 不需要知道 DB schema, 只关心 history slice; service 知道 DB schema, 实现 history 查询。

教训: **抽象边界用 interface 而不是直接接 DB, 更解耦 + 更易测试**。

**§2.1 轻度触及 — 用户拍板即可**

新意度检查触及 §2.1 (辩论结果评判的一种), 但:
- 阈值 0.6 是客观数学 (PRD §4.3.3 已规定)
- retry 行为 + fallback 是用户拍板 (本次直接 2 次 retry + fallback)
- 不引入新裁决类型, 不动 oscillation → finishTrial 通路

教训: **§2.1 触及程度有"轻度 / 中度 / 强"区分**。本次轻度, 用户拍板即实装。中度 (e.g. LLM-as-judge stance) 需 4 个判定标准讨论。强 (e.g. 反驳证据有效性) 需先讨论后做。
