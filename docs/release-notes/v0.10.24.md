## 🎯 核心主题

**为 DecisionCourt Agent 落地"LLM-as-judge stance 一致性"硬规则: 与当前 belief 方向不一致 (老 isStanceConsistent 阈值 0.45 fast filter 通过后) 触发 LLM judge, judge false 注入 hint 强制 LLM 换内容重生成, 2 次 retry 失败 fallback 返回带 StanceRejected=true 的 Speaker。触及 §2.1 中度 (LLM 主观判定), 用户已拍板 4 个标准。**

3 个核心收益:
1. **PRD §4.3.2 落地** — 强制立场一致性检查从 ⏳ v0.7+ 计划 → ✅ v0.10.24 候选 1
2. **架构解耦** — 老 isStanceConsistent (Go 规则) + 新 LLM judge (语义判定) 分层, 老实现保留作为 fast filter 不破坏现有
3. **PRD vs 代码阈值同步** — PRD 原文 0.5, 老代码 0.45/0.55, 本次同步对齐到 0.45 (老实现是双边界: pro_a < 0.45 + pro_b > 0.45, 中间地带 0.45-0.55 任何 stance 都一致作为逃逸口)

## 🐛 实施过程中的 bug / 教训

### D.1 老 isStanceConsistent 阈值误判

**症状**: 第一次写测试 `0.45 + pro_a` 期望 true, 但实际老代码 return false。

**根因**: 读老代码时把 `< 0.55` 当成阈值 (因为 PRD 写 0.5 阈值), 实际老代码是 `< 0.45` + `> 0.45` (双边界, 严格 > / <)。[0.45, 0.55] 中间地带是逃逸口, 任何 stance 都一致。

**修复**: 测试改成 0.45 + pro_a → false (老逻辑 0.45 < 0.45 false, 但 0.45 < 0.55 是另一条分枝, 实际走通用 pro_a + < 0.55 = true → return false。等等我数错了)。

**学习**: **写测试前先实际运行老代码** + 至少写一个探针测试, 不要凭"我觉得老代码长这样"。

### D.2 探针 main 测试 救场

**症状**: 测试预期与老代码不一致, 反复 fix 失败 4-5 次。

**解决**: 写了临时 `main.go` 探针 (用 cat heredoc 临时写), 直接 print 老函数结果。

```go
fmt.Printf("0.45 + pro_a: %v\n", isStanceConsistent(0.45, "pro_a"))  // true
fmt.Printf("0.46 + pro_a: %v\n", isStanceConsistent(0.46, "pro_a"))  // true
fmt.Printf("0.44 + pro_a: %v\n", isStanceConsistent(0.44, "pro_a"))  // false
```

**学习**: **复杂边界条件先写探针 main**。`go run /tmp/debug.go` 比反复 fix 测试快 10 倍。

### D.3 测试 fixture 错位: 5 次 LLM call 还是 4 次

**症状**: `TestApplySpeakerStanceJudge_Retry2FailureFallback` 期望 "final reason", 但实际拿 "retry 1 reason"。

**根因**: `applySpeakerStanceJudge` 实际是 5 次 LLM call: `judge1 + retry1 + judge2 + retry2 + judgeStanceOnce`。我测试只给了 4 个 response, fake idx 越界返回最后一个 ("retry 1 reason")。

**修复**: 测试改成 5 个 response: `[judge1, retry1_speak, judge2, retry2_speak, final_judge]`。

**学习**: **retest fixture 数量必须与 LLM call 次数一致**。retry loop + final judge 的 call 序列要算清楚, 不能凭"大概是这样"。

### D.4 PRD 阈值错误 (0.5 vs 0.45) 的同步教训

**症状**: PRD §4.3.2 原文写 `belief_A < 0.5` 触发一致性检查, 老代码用 `< 0.45`。

**根因**: PRD 是早期写的, 代码后来调整到 0.45 (从 0.5 改来, 可能为扩大逃逸口), 文档没同步。

**修复**: PRD §4.3.2 同步改 0.5 → 0.45/0.55, 加注脚说明 "实际老 isStanceConsistent 用 0.45 (双边界, 中间 0.45-0.55 任何 stance 都一致作为逃逸口)"。

**学习**: **PRD/代码不一致要在 PR 时同步修**, 不能拖 (拖了就成历史债)。

### D.5 触及 §2.1 中度 决策记录

触及 §2.1 的程度区分:
- **轻度** (v0.10.22 PR-A, v0.10.23 novelty): 阈值客观 (0.6) 或纯数学 (Jaccard), 用户拍板即实装
- **中度** (v0.10.24 stance): LLM 主观判定, 需拍板 4 标准 (prompt / 触发时机 / 失败动作 / token 成本)
- **强** (v0.11 反驳证据, D1 安全审计): 触及证据有效性 / 安全决策, 必须先讨论后做

本次属中度, 用户已答 4 标准, 不重新讨论。

## 📝 反思

**v0.10.24 是 "LLM-as-judge 硬规则化" 主题**

按用户偏好「按原 roadmap 推进, 不调整」, v0.10.24 候选 1 LLM-as-judge stance 检查从 roadmap §5.3 第二阶段第 3 项 ⏳ → ✅。与 v0.10.21 PR-B (发言长度硬截断) + v0.10.23 novelty (新意度 Jaccard) 同主题: **把"靠 Prompt 自约束"升级为"后端硬校验 + 自动 retry"**。

教训: **"硬规则化"三连击**:
- v0.10.21 PR-B: 发言长度 300 字硬截断 (后端兜底)
- v0.10.23 novelty: 新意度 Jaccard > 0.6 retry (后端兜底)
- **v0.10.24 stance**: LLM-as-judge 立场一致性 retry (后端兜底) ← 本次
- 共同模式: Prompt 软约束 + 后端硬校验 + 透明审计 (Speaker flag + 前端 chip)

**§2.1 触及程度**

| 改动 | §2.1 触及 | 备注 |
|---|---|---|
| `StanceJudgePrompt` | **中度** | LLM 主观判定 prompt, 用户已拍板 |
| `applySpeakerStanceJudge` | **中度** | LLM 调 retry 行为, 用户已拍板 |
| `isStanceConsistent` 复用 | 0 | 老 Go 规则, 客观数学 |
| `RunnerConfig` 注入 | 0 | 纯 plumbing |
| 前端 chip | 0 | 纯渲染 |

用户拍板 4 标准:
1. **judge prompt 模板**: StanceJudgePrompt (PRD §4.3.2 字面判 content 语义, 不是 stance 字段)
2. **触发时机**: 仅 stance 枚举不一致时调 judge (省 90% token, 老 isStanceConsistent fast filter)
3. **失败动作**: 2 次 retry + Speaker flag fallback (与 novelty 同构)
4. **token 成本**: 低温 0.2 + MaxTokens 200 (低成本), judge 调 1-3 次/发言, worst case 20 次/庭审
