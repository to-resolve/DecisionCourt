## 🎯 核心主题

**修复 v0.10.18 部署失败的 root cause：viper 1.21.0 的 `AutomaticEnv()` 把 `JWT_SECRET` 自动转 `jwt_secret` 查环境变量，结果在容器里设置的大写 env 找不到。** 用 5 行显式 `BindEnv()` 绑定 5 个关键 env，立刻可部署。

---

## 🐛 Bug 根因

**症状**：v0.10.18 部署后 backend 启动 FATAL：

```
FATAL: required config JWT_SECRET is empty
```

但容器 env 实际有 `JWT_SECRET`（`docker compose config` + `docker compose run --rm backend env` 双确认）。

**根因**（`bd47599` commit message 总结）：
- `viper.AutomaticEnv()` 把 key `JWT_SECRET` 自动转 `jwt_secret` 查环境变量
- 容器里只设了 `JWT_SECRET=...`，找不到 `jwt_secret`，拿默认值
- v0.10.17 之前有 `SetDefault("JWT_SECRET", "decisioncourt-secret")`，bug 被默认值掩盖
- v0.10.18 删除默认值后，bug 立刻暴露 → P0-2 fail-fast 触发，把 viper bug 摆到台面

---

## 🛠 修复方案

`backend/internal/config/config.go Load()` 加 5 行显式 `BindEnv()`：

```go
// 关键 env 显式绑定（viper 1.21.0 AutomaticEnv 自动小写化的 workaround）
viper.BindEnv("JWT_SECRET")
viper.BindEnv("DATABASE_URL")
viper.BindEnv("LLM_API_KEY")
viper.BindEnv("BOCHA_API_KEY")
viper.BindEnv("ALLOWED_ORIGINS")
```

**为什么是这 5 个**：
- `JWT_SECRET`：P0-2 fail-fast 触发的元凶，无默认值必须有
- `DATABASE_URL`：P0-4 mustEnvs，无默认值必须有
- `LLM_API_KEY`：业务关键，必填
- `BOCHA_API_KEY`：搜索 provider，必填（生产）
- `ALLOWED_ORIGINS`：WS CheckOrigin 白名单，v0.9.3 单值 split bug 历史教训

**其他 25+ env**：继续走 `AutomaticEnv`（lowercase 查找），但因 `SetDefault` 有默认值，**不会因为 viper bug 启动失败**——只会拿默认值不拿真实 env（影响范围小，不在本次修复范围）。

**后续规划（v0.11+）**：重写 `Load()` 用 helper `envOrFatal()`，绕过 viper 自动绑定机制，全面修剩余 25+ env 的 lowercase 问题。详见 [ADR 0026](../adr/0026-viper-bindenv-fix.md) §3 后续工作。

## 📝 反思（2026-08-05 retrospective）

**为什么 v0.10.19 没有错位**：

v0.10.19 状态栏在发布时已写"✅ 已部署 ECS"。但因后续 commit `cbbaf3d` (v0.10.20) 紧接部署，v0.10.19 release notes 文件**未单独创建**——直接在 v0.10.20 的 commit message 里引用 v0.10.19。直到 2026-08-05 30 天生产沉淀时才补上独立 release notes 文件（本文件）。

**教训**：发布流程的最后一步应包含"git push tag → 立即创建对应 release notes 文件"，避免版本号跳号。本次补全作为 v0.10.21 的 release notes 准备前置工作。
