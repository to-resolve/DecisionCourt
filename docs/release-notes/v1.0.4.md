## 🐛 实施过程中的 bug / 教训

### D.1: Run.TraceID 字段映射（plan vs 实际）

**问题**：plan §1.3 设计的字段名是 `trace_id`，但实际 `agent_gateway.LogEntry` 字段是 `request_id`（v0.10.22 PR-A 沿用 HTTP middleware `X-Request-ID` 注入）。

**教训**：
- 解析时 `Run.TraceID = LogEntry.RequestID`，JSON tag 用 `json:"trace_id"` 保持 API 命名一致
- 与 `observability.Trace.RequestID` 字段对齐（logger.go 注释"与 agent_gateway.Trace 复用 trace_id 字段，不重复发明轮子"）
- 未来切换 OTel 时不改 API 字段名（OTel 标准就是 `trace_id`）

### D.2: FileTraceStore 缓存 key 设计

**问题**：第一版按 `"sessionID:" + date` 缓存，导致多 session 同一天文件重复解析。

**教训**：
- 改为 `"file:" + date` 文件级缓存，跨 session 复用解析结果
- LRU key + cache 实现用 `container/list` + `map` 自实现，避免引第三方 LRU 库
- session 过滤在内存里做（`filterSession`），不破坏缓存复用

### D.3: Itinerary 解析错误计数

**问题**：单行 JSON 解析失败时，第一版想 return error 终止整个解析，导致 1 行损坏丢失所有数据。

**教训**：
- 改为"跳过该行 + parseErrors+1，继续解析"语义
- 累计 parseErrors 返给调用方做埋点 / 日志
- `os.ErrNotExist` 检查也修了：`fmt.Errorf("...: %w", err)` 包装后用 `errors.Is(err, os.ErrNotExist)` 比 `os.IsNotExist(err)` 更可靠

### D.4: 前端测试 ESM + .ts 后缀 + fetch mock 复杂度

**问题**：第一版想 mock `globalThis.fetch` 验证 `fetchTraces` 解析响应。但 ESM 模式下 `globalThis.fetch =` 在 import hoisted 后失效，加上 Node `--test` 默认 `typeof window === "undefined"` 永远走 SSR 返空路径。

**教训**：
- SSR-safe 路径是产品要求（Next.js build 时不能 fetch），必须测试 → 写 4 个 SSR 测试
- fetch 路径测试需要 jsdom 环境，按 v1.0.2 D.2 教训（ESM + .ts 后缀 + fetch mock 链路复杂），本 PR 不引入
- 在 `lib/trace.test.ts` 注释里文档化"浏览器路径未测" + "运行时按 SSR-safe 契约兜底"

### D.5: Framer Motion 与 CSS 动画共存

**问题**：第一版想全替换 AgentAvatar 现有 CSS `transition-all` + `animate-pulse` + `animate-spin` 为 motion 动画。

**教训**：
- 保留 CSS 装饰元素（spinner ring / cursor blink）— 它们无状态切换需求
- motion 接管"有状态的"头像+气泡 — 6 个 variants + AnimatePresence
- 性能 + 维护性权衡：少引 ~5KB 代码 + 不破坏既有 CSS 测试覆盖

### D.6: Aggressive Shell 引号

**问题**：commit message 含反引号 (`下一步`) 时 Git Bash 把引号当 quote 截断，导致 commit 失败。

**教训**：
- 改用 `git commit -F <file>` 模式：把 commit message 写到文件，再从文件读
- 适合多行 commit message + 避免 shell 转义陷阱
- 写一个 temp file + commit + 删 temp file（自动化 PR 时）
