## 🐛 实施过程中的 bug / 教训

### D.1: dev compose 启动配置脆弱（PR-B1 启动验证踩 3 个坑）

**问题**: PR-B1 完成后跑真实 trial 验证，发现 dev compose 在 Windows 上:
- 端口 8080 与其他项目冲突 → 改 8180
- `.env` 残留生产域名 → `NEXT_PUBLIC_*` 必须 hardcode 覆盖
- `ALLOWED_ORIGINS` 缺失 → CORS preflight 失败

**教训**:
- Dev compose 启动配置应该在 `docker-compose.yml` 写死，而不是依赖 `.env`
- 任何新增 `NEXT_PUBLIC_*` 变量都要 hardcode 默认值（避免误用生产域名）
- `ALLOWED_ORIGINS` 也 hardcode 到 `cmd/server/main.go`（dev 默认 `localhost:3000`，prod 靠 env 覆盖）

### D.2: D2 silent error 复现（cross-exam content 空）

**问题**: 用户启动验证时发现某些 trial 的 cross-exam 阶段发言记录全空，但前端没报错。
**根因**: `streamSpeakContent` 流式解析失败时静默 fallback 到空字符串，没拦截。
**教训**: silent error 黑洞防御必须在 persist 边界做（`saveAgentMessage` 拦截空 content），不能依赖流式解析成功。

### D.3: D3 direct_verdict fallback "共 0 轮"

**问题**: 用户跳过 cross-exam 直接判决时，判决书显示"本场庭审共 0 轮"（实际跑了 3 轮）。
**根因**: `cancelCall` 触发 ctx cancel 跨 `finishTrial`，加 `transitionPhase(closing, 0)` 重置 round。
**教训**: phase transition 的 round 参数必须从 DB / 消息表读真实值，不能传 0 当 "default"。

### D.4: ArgumentMap 反馈驱动移除

**问题**: 用户反馈"ArgumentMap 完全没用 — 我看叙事流就够"。
**教训**:
- 任何 UI 组件的"信息图重写"都要警惕 — 叙事流已承载信息时，ReactFlow 等重写组件不会提供额外洞察
- ADR 0009 当年就提了方案 C（移除 ArgumentMap），v1.0.3 终于落地
- 卸 `reactflow` 依赖减少 ~150KB bundle

### D.5: 测试期望搞反（abtest_test.go Winner 方向）

**问题**: 第一版测试 `TestABTest_LLMRuleScoresAlignment` 期望 `Winner=B` 但实际 `Winner=A`。
**根因**: 我设计 responses 数组时假设 "judge 给 A 高分"，但 abtest.go 实现是 `MeanA > MeanB → Winner=A`（A 赢 = A 的分数高）。
**教训**: 单测 mock 的 `responses` 序列必须严格对应实现调用顺序（A[0]、B[0]、A[1]、B[1]），不能凭直觉。

## ⏸ 已知遗留 / 下一步

### PR-B2 A/B Test 设计妥协

当前 A/B Test 不区分 version 的 prompt 内容，对同一 output 走相同 Eval → 确定性规则上必然 tie。
**完整 A/B Test 需要**:
1. "按 version 切换 prompt 跑 trial" — prompt 版本 → LLM 调用路由
2. 重新跑 LLM 拿 A/B 输出
3. 再 eval 两份输出比较

**触及 §2.1 裁决逻辑: 轻**（是评分比较框架的扩展，不动庭审语义）
**下一步**: v1.0.4 + v2.0 完成后，启动 v1.0.x 后续 PR 时做

### /prompts/reload 无 admin 鉴权

当前任何登录用户都能触发 manual reload。理由: reload 是只读 + swap ~毫秒级不烧 CPU/IO；项目当前 auth 是匿名 JWT 无 admin role 概念。
**下一步**: 引入 admin role 后（v1.1 商业化前置 M2），在 handler 内部加 viewer 白名单判断，接口签名无需变化。

### Eval 评分不稳定
